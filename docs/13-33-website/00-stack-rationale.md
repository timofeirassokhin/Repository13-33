# Стек для 13-33.pro — обоснование

## Краткая рекомендация

**Payload CMS 3 + Next.js 15 (App Router) + Postgres + pgvector + Cloudflare**.

Self-hosted на том же RU VPS (где CRM/MemPalace/uploader). TypeScript end-to-end. Агенты работают со схемой и публикацией через REST/GraphQL.

---

## Payload vs Astro — разбор по осям

Astro — отличный инструмент, и для контентного сайта первый кандидат. Я его не выбрал не потому что он "хуже", а потому что **наш сайт — не контентный сайт. Это граф с CMS-наполнением**.

### Ось 1. Природа данных

**Astro** — content-first, статика. Контент живёт в файлах (MDX/Markdown в репо или подключённой headless CMS). Сильнейший SSG: страницы рендерятся на билде. Идеален когда:
- контент пишут в репо или в одной headless CMS
- структура простая (посты, страницы, теги)
- редкие обновления

**13-33.pro — не такой**:
- 5 коллекций объектов с **многосторонними связями** (статья ↔ метод ↔ тема ↔ запрос ↔ продукт ↔ эксперт ↔ событие)
- Будут квизы с динамическим результатом-треком
- Нужен поиск (сейчас текстовый, потом семантический через pgvector)
- Будут редакторы (твои + эксперты), которые правят контент через админку, не через git
- Кросс-связи рассчитываются на сервере, не на билде
- Аналитика и фидбек собираются с первой страницы

Это **headless CMS + ssr-приложение**, а не SSG-блог. Astro можно сюда натянуть, но мы будем строить недостающую CMS поверх него — то есть переизобретать Payload.

### Ось 2. Гибкость и рост

**Astro**: добавить новый тип контента — это либо новый MDX-фронтматтер (быстро, но не валидируется), либо новая коллекция в подключённой CMS (тогда работа идёт в той CMS — Sanity/Strapi/Directus, а не в Astro). Чем сложнее граф, тем меньше Astro помогает.

**Payload**: новый тип контента = новая коллекция в TS-схеме → миграция Postgres → автогенерируемая админка → автогенерируемый REST/GraphQL. **Агент** правит TS-схему, накатывает миграцию, и новый раздел доступен для редактуры. Это та "максимальная гибкость" что ты просил.

### Ось 3. Производительность и SEO

**Astro** выигрывает на чистом SSG → пустячный TTFB, идеальный Lighthouse.

**Next.js + Payload**: ISR (incremental static regeneration) + кеш Cloudflare → почти то же самое для публичных страниц. Карточки продукта, статьи, страницы тем — всё статика с ревалидацией. Динамика только там, где надо: квиз-результат, ЛК, корзина, поиск.

Разница в Lighthouse — единицы баллов. На реальной перцепции пользователя — не ощутимо.

### Ось 4. Эксплуатация

**Astro**: тонкий рантайм, статика на CDN. Просто и дёшево.

**Payload**: нужен Postgres, Node-процесс админки, S3-совместимое хранилище для медиа. Чуть сложнее, но у нас уже есть Postgres на сервере, S3-минио поднять — час работы.

### Ось 5. AI-готовность

Это тот пункт, который ты явно спросил.

**Astro**: код-ориентирован, агент пишет MDX-файлы. Но если контент в подключённой CMS — агент должен работать через API той CMS. Нет единой схемы.

**Payload**: схема — TypeScript, лежит в репо. Агент:
- читает схему → понимает структуру → пишет/правит контент через REST/GraphQL
- расширяет схему (новая коллекция / поле) → запускает миграцию → готово
- генерирует страницы экспертов из их статей и продуктов
- автотегирует входящие материалы по трём осям (темы/запросы/методы)
- делает кросс-ссылки на основе совпадения тегов

Это та самая **сборка на агентах поверх CMS**. Twenty CRM остаётся для workflow редакции (Idea → Draft → Publication), Payload — для публикации и хранения опубликованного контента, агенты — для оркестровки между ними.

## Когда Astro был бы правильным выбором

Если бы 13-33.pro был **только журналом** (статьи + теги + автор + страница "о нас"), без магазина, без квизов, без графа экспертов/методов/продуктов, без Арбата — Astro уверенно. Но архитектура которую ты обрисовал — это полноценная контент-платформа.

## Стек целиком

| Слой | Выбор | Причина |
|---|---|---|
| Frontend framework | **Next.js 15 (App Router)** | RSC, ISR, edge-friendly, нативная интеграция с Payload |
| CMS / backend | **Payload 3** | TS-схема, REST + GraphQL, админка из коробки, self-host |
| База | **Postgres 16 + pgvector** | реляционка под граф связей + векторный поиск (V2) |
| Хранение медиа | **S3-совместимое (MinIO)** | self-host на том же VPS |
| Стили | **Tailwind CSS + CSS variables** | дизайн-токены через переменные, легко подстроить под Figma |
| UI-кит | **shadcn/ui** | копируется в репо, можно править под бренд |
| Анимации | **Framer Motion** | по необходимости, дозированно |
| Аналитика | **Plausible** (self-hosted) | приватность, GDPR-ок, без cookie-баннеров |
| Поиск V1 | **Postgres FTS** | бесплатно, достаточно |
| Поиск V2 | **pgvector + OpenAI/локальные embeddings** | семантический поиск, связь с MemPalace |
| Auth | **Payload Auth** (V2) | для ЛК, пока вход через GetCourse |
| CDN / WAF | **Cloudflare** | кеш, защита, CN-блок не критичен |
| CI/CD | **GitHub Actions → Docker → VPS** | стандартно |
| Мониторинг | **Sentry + Plausible** | ошибки + продуктовые метрики |

## Что **не** берём и почему

- **Sanity / Contentful** — отличны, но vendor lock + платежи, и схема правится медленнее
- **Strapi** — open-source, но JS-only без строгого тайпинга, экосистема слабее Payload
- **WordPress** — нет, у нас не блог
- **Tilda / Webflow** — годятся для одного лендинга, но не для графа из 7 типов контента и квизов
- **Custom from scratch без CMS** — строить админку самим = месяцы работы. Payload даёт её бесплатно
